All traces below were produced with `python3 process-run.py ... -c -p`.
Default I/O length is 5 ticks: an `io` instruction takes 1 tick on the CPU, the
process is BLOCKED for the next 5 ticks, and the `io_done` instruction runs on
the CPU afterwards (so a single I/O costs 2 CPU ticks + 5 I/O ticks).

## Q1. `-l 5:100,5:100`

Both processes only use the CPU, so the CPU is never idle.
**CPU utilization = 100%** (10 of 10 ticks). Process 0 runs ticks 1–5 while
process 1 is READY; process 1 runs ticks 6–10.

## Q2. `-l 4:100,1:0`

Process 0 has 4 CPU instructions; process 1 has one I/O (`io`, `io_done`).
Process 0 runs first (ticks 1–4), then process 1 issues its I/O at tick 5,
is BLOCKED for ticks 6–10 while the CPU sits idle, and runs `io_done` at tick 11.

**Total time = 11 ticks** (CPU busy 6/11 = 54.55%, I/O busy 5/11 = 45.45%).

## Q3. `-l 1:0,4:100`

Now the I/O-bound process runs first. It issues its I/O at tick 1 and becomes
BLOCKED; with the default `SWITCH_ON_IO` the OS switches to process 1, which
runs its 4 CPU instructions (ticks 2–5) *while* the I/O is in progress. Tick 6
is idle (process 1 done, I/O still running) and `io_done` runs at tick 7.

**Total time = 7 ticks** (CPU 85.71%, I/O 71.43%).

Yes, the order matters: starting the I/O first lets CPU work overlap with the
I/O, so the run is 4 ticks shorter than in Q2. In Q2 the I/O was only issued
after all CPU work finished, so nothing could overlap with it.

## Q4. `-l 1:0,4:100 -S SWITCH_ON_END`

With `SWITCH_ON_END` the OS will not switch away from a process until it
finishes, even when it is BLOCKED on I/O. Process 0 issues its I/O at tick 1
and the CPU is idle for ticks 2–6 while process 1 waits in READY. Process 0
finishes with `io_done` at tick 7, then process 1 runs ticks 8–11.

**Total time = 11 ticks** (CPU 54.55%) — the same as Q2, because no overlap
of CPU and I/O is possible.

## Q5. `-l 1:0,4:100 -S SWITCH_ON_IO`

Identical to Q3 (`SWITCH_ON_IO` is the default). When process 0 blocks on its
I/O, the OS switches to process 1, which uses the CPU during the I/O.

**Total time = 7 ticks** (CPU 85.71%, I/O 71.43%).

## Q6. `-l 3:0,5:100,5:100,5:100 -S SWITCH_ON_IO -I IO_RUN_LATER`

- Tick 1: P0 issues its first I/O; OS switches to P1 (ticks 2–6).
- Tick 7: P0's I/O completes, but with `IO_RUN_LATER` P0 only moves to READY.
  The scheduler picks the next READY process after the current one, so P2
  runs (ticks 7–11), then P3 (ticks 12–16).
- Only at tick 17 does P0 get the CPU back. It then issues its remaining two
  I/Os one after another, and since no other process is left, the CPU is idle
  during each of them (ticks 19–23 and 26–30).

**Total time = 31 ticks, CPU busy 21/31 = 67.74%, I/O busy 15/31 = 48.39%.**

System resources are **not** used effectively. The I/O device is idle from
tick 7 to tick 18 while the CPU-bound jobs run, and afterwards the CPU is
idle while P0's last two I/Os are serviced. If P0 had been allowed to issue
its next I/O as soon as its first one completed, both of those I/Os could have
overlapped with the CPU-bound processes.

## Q7. same as Q6 but `-I IO_RUN_IMMEDIATE`

Now, when P0's I/O completes, the OS immediately switches to P0 (the current
process is moved to READY). P0 runs `io_done` and immediately issues its next
`io`, then blocks again, and the OS switches back to a CPU-bound process:

- ticks 7–8: P0 `io_done` + `io`, ticks 9–13: P2
- ticks 14–15: P0 `io_done` + `io`, ticks 16–20: P3
- tick 21: P0's last `io_done`

**Total time = 21 ticks, CPU busy 21/21 = 100%, I/O busy 15/21 = 71.43%.**

Every I/O now overlaps with CPU work, so the CPU is never idle and the job
finishes 10 ticks sooner. Running a process that just finished an I/O is a
good idea because such a process is usually I/O-bound: it will run for a very
short time and then issue another I/O. Scheduling it right away keeps the I/O
device busy while it gives the CPU back quickly to the CPU-bound processes, so
both resources are used in parallel. (It also improves responsiveness for
interactive programs, which are typically I/O-bound.)

## Q8. Randomly generated processes, `-l 3:50,3:50` with seeds 1, 2, 3

Programs generated by each seed:

| seed | Process 0 | Process 1 |
|---|---|---|
| 1 | cpu, io, io_done, io, io_done | cpu, cpu, cpu |
| 2 | io, io_done, io, io_done, cpu | cpu, io, io_done, io, io_done |
| 3 | cpu, io, io_done, cpu | io, io_done, io, io_done, cpu |

Total time (ticks) for each flag combination:

| seed | SWITCH_ON_IO + IO_RUN_LATER | SWITCH_ON_IO + IO_RUN_IMMEDIATE | SWITCH_ON_END + IO_RUN_LATER | SWITCH_ON_END + IO_RUN_IMMEDIATE |
|---|---|---|---|---|
| 1 | 15 (CPU 53.33%) | 15 (CPU 53.33%) | 18 (CPU 44.44%) | 18 (CPU 44.44%) |
| 2 | 16 (CPU 62.50%) | 16 (CPU 62.50%) | 30 (CPU 33.33%) | 30 (CPU 33.33%) |
| 3 | 18 (CPU 50.00%) | 17 (CPU 52.94%) | 24 (CPU 37.50%) | 24 (CPU 37.50%) |

Observations:

1. **`-S` matters much more than `-I`.** `SWITCH_ON_END` is always slower,
   because the CPU sits idle during every I/O instead of running the other
   process. The penalty is largest for seed 2, where both processes do two
   I/Os each: with `SWITCH_ON_IO` their I/Os overlap (up to 2 I/Os in flight
   at once, I/O busy 87.5%), while with `SWITCH_ON_END` all four I/Os run
   one after another (30 ticks, almost twice as long).

2. **With `SWITCH_ON_END`, `-I` makes no difference.** Only one process can
   ever have an I/O in flight — the one that holds the CPU — so when its I/O
   completes there is nobody else to preempt, and "run later" and "run
   immediately" produce the same trace.

3. **With `SWITCH_ON_IO`, `-I` only matters when an I/O finishes while the
   *other* process is running on the CPU.** In seeds 1 and 2 every I/O
   completes while the CPU is idle or the other process is itself blocked, so
   both options give the same trace. In seed 3, P1's I/O completes at tick 9
   while P0 is running its final `cpu`:
   - `IO_RUN_LATER`: P0 finishes its `cpu`, then P1 runs `io_done` (tick 10)
     and issues its second I/O at tick 11. That I/O runs alone while the CPU
     is idle, so the run ends at tick 18.
   - `IO_RUN_IMMEDIATE`: P1 preempts P0 at tick 9, issues its second I/O at
     tick 10, and P0's `cpu` runs at tick 11 *during* that I/O. The run ends at
     tick 17, one tick sooner.

   This is the same effect as in Q7 on a small scale: giving the CPU to the
   process that just finished its I/O gets its next I/O started sooner, so
   more CPU work overlaps with I/O.
